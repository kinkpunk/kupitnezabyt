# План исследования первых пользователей и backlog доработок

Дата: 2026-07-21.
Основание: `docs/IMPLEMENTATION_ROADMAP.md`, `docs/PRODUCT_SPEC.md`,
`docs/FINAL_INTEGRATION.md`, история коммитов.

Контекст: у сервиса есть два реальных пользователя — автор и ещё один человек,
использующий сервис в повседневной жизни. Второй пользователь — готовый
респондент №1 с накопленным опытом (ценнее рекрутированного новичка: у него
есть ответы на вопросы блока C без всякой сессии). Шаринг списков
(collaboration) уже используется в жизни и работает, поэтому ручной
двухаккаунтный smoke из Slice 32 не требуется; крайние случаи будем
исправлять по факту обнаружения.

Документ состоит из двух частей:

1. **Backlog доработок**, собранный из известных пробелов между спецификацией,
   роадмапом и реализацией — не требует опроса пользователей.
2. **Опросник для пользователей** и план рекрутинга: блоки A и C применимы ко
   второму пользователю уже сейчас, блок B и второй круг рекрутинга — после
   открытия доступа следующим 5–10 пользователям.

## Часть 2. Опросник для первых бета-тестеров

### 2.1 Принципы

- Это скрипт полуструктурированного интервью (30–40 минут) + короткая анкета,
  а не массовый опрос. Для 5–10 человек открытые вопросы ценнее шкал.
- Каждый вопрос привязан к гипотезе и к задаче, которую он может породить.
  Вопрос без «что мы сделаем с ответом» не задаём.
- Сначала смотрим на поведение (просим выполнить сценарии вживую), потом
  спрашиваем мнение. Мнение без наблюдения обманывает.
- Личные заметки, лекарства и гигиена — чувствительные данные (см. `AGENTS.md`).
  Не просим показывать реальные содержимые списков, не записываем их в протокол.

### 2.2 Гипотезы, которые проверяем

| # | Гипотеза | Источник |
|---|----------|----------|
| H1 | Цикл «добавить → отметить статус → получить список покупок» понятен без объяснений | PRODUCT_SPEC §3, §7.5, §7.7 |
| H2 | Периодические проверки (check cycles) — главная удерживающая ценность, а не список покупок сам по себе | PRODUCT_SPEC §7.6, §7.10 |
| H3 | Rule-based рекомендации воспринимаются как помощь, а не спам | PRODUCT_SPEC §7.8 |
| H4 | In-app напоминаний достаточно; внешние каналы (Telegram/email/push) не критичны для MVP | Roadmap web-first pivot 2026-06-21 |
| H5 | Совместные списки (workspace) нужны реальным людям, а не только в спеке | Slices 27–32 |
| H6 | Вход через magic link не отпугивает на первом шаге | PRODUCT_SPEC §7.1 |

### 2.3 Блок A. Профиль (анкета, 5 минут, до сессии)

1. Возрастной диапазон: до 25 / 25–35 / 35–45 / 45+.
2. Кто в доме обычно следит за запасами (я / партнёр / поровну / никто)?
3. Чем сейчас пользуетесь для списков покупок и напоминаний? (заметки, бумага,
   другие приложения, память) — *даёт список конкурентов и базовую линию.*
4. Случалось ли за последний месяц: закончилось что-то важное в неподходящий
   момент? Что именно? — *проверка, что проблема вообще существует; если у всех
   «нет», ставка продукта под вопросом.*
5. Какие категории расходников для вас актуальны? (еда / аптека / косметика /
   бытовая химия / питомцы / авто / другое) — *сверка с набором категорий
   в спеке; может породить задачи на предзаполненные категории.*

### 2.4 Блок B. Наблюдаемые сценарии (модератор молчит, фиксирует)

Просим выполнить на тестовом аккаунте, озвучивая мысли вслух:

1. **Вход**: зайти в сервис по ссылке. *(H1, H6; где споткнулся — задача на
   auth UX.)*
2. **Онбординг**: пройти первые экраны. Понятно ли, чем сервис отличается от
   списка покупок? *(H1; если «непонятно» — задача на онбординг/копирайтинг.)*
3. **Ядро**: добавить 3 реальных товара из своей жизни, выставить статусы.
   *(H1; смотрим на выбор статусов `LOW/NEED_BUY/URGENT` — понятна ли
   градация; если путаются — задача на naming/UX статусов.)*
4. **Список покупок**: найти, какие товары попали в список покупок и почему.
   *(Проверка видимости связки статус → список.)*
5. **Проверка**: пройти пошаговый режим проверки (check session). *(H2;
   ключевой сценарий удержания — здесь замеряем время и число ошибок.)*
6. **Рекомендации**: отреагировать на предложенный связанный товар.
   *(H3; «добавил» / «скрыл похожие» / «раздражает» — три разных outcome.)*

После каждого сценария один вопрос: «Что здесь было не так, как вы ожидали?»

### 2.5 Блок C. Мнение и ценность (после сценариев)

1. Что из увиденного вы бы использовали через неделю? Через месяц? —
   *разделяет «вау при первом контакте» и удержание.*
2. Чего не хватило, чтобы добавить ВСЕ свои регулярные покупки? —
   *прямой источник задач; ожидаемые ответы: импорт, важность (B1), порядок
   товаров (B2), наборы.*
3. Напоминание внутри приложения вы заметите? Что было бы лучше: Telegram,
   email, push? *(H4; ответ определяет судьбу B3 и приоритет worker-а.)*
4. С кем бы вы вели такой список совместно? Попробовали бы пригласить? —
   *(H5; валидация collaboration beta до дальнейших вложений.)*
5. Представьте, что сервис завтра закрылся. Что вы потеряли? —
   *классический вопрос product/market fit; «ничего» у большинства = сигнал
   пересмотреть ценностное предложение.*
6. Что бы вы удалили из сервиса без сожаления? — *защита от раздувания
   функциональности.*

### 2.6 План рекрутинга

1. **Нулевой шаг (запланировано, будет проведено позднее):** интервью со вторым
   существующим пользователем по блокам A и C — у него накопленный реальный
   опыт, сессия со сценариями блока B не обязательна.
2. Предусловие для дальнейших кругов: закрыта задача B10 (B9 и B12 выполнены —
   вход через Google работает, прод-URL зафиксирован и прошёл smoke; остаётся
   внешняя часть Apple sign-in).
3. Первый круг: 5–7 человек из ближнего круга, ведущих домашнее хозяйство;
   формат — созвон с шарингом экрана или лично, 30–40 минут.
4. Второй круг (после исправления находок первого круга): 5–10 человек из
   тематических чатов; формат — самостоятельное прохождение + анкета блоков A и C.
5. Критерий остановки исследования: два круга подряд не дают новых задач
   в backlog.
6. Протокол каждой сессии: дата, сегмент, наблюдения по сценариям, список
   порождённых задач. Без персональных данных и содержимого списков.

### 2.7 Как ответы превращаются в задачи

Каждая находка классифицируется:

- **Баг/трение** (споткнулся в сценарии) → задача сразу, приоритет по частоте
  повторения у разных тестеров.
- **Отсутствующая ценность** (блок C, п.2) → кандидат в роадмап, сверка со
  спекой §19, чтобы не тянуть post-MVP раньше времени.
- **Опровергнутая гипотеза** (H1–H6) → не задача, а решение: менять копирайтинг,
  приоритет или судьбу целого направления (например, Telegram-интеграции).
